# Модель поиска валуйных ставок — UAE Pro League

Бот присылает ставки в Telegram: [@betspredictionuaebot](https://t.me/betspredictionuaebot)

## Автоматический режим

Три воркфлоу GitHub Actions закрывают весь цикл — от сбора данных до расчёта
результата. Руками не делается ничего.

| Когда (UTC) | Что | Воркфлоу |
|---|---|---|
| **каждые 30 мин, 05:00-21:59** | сторож: не открылась ли линия, не появился ли матч, не сдвинулась ли цена | `uae-watch.yml` |
| при изменении | полный расчёт и отправка ставок | `uae-watch.yml` |
| 09:17 и 12:47 | гарантированные прогоны на случай сбоя сторожа | `uae-bets.yml` |
| 13:33 и 16:03 | зафиксировать закрывающую линию Pinnacle (за 12 мин до стартов) | `uae-clv.yml` |
| 19:23 | рассчитать сыгравшее, прислать сводку по CLV и ROI | `uae-settle.yml` |

### Почему сторож отдельно

Полный расчёт переобучает модель заново перед каждым игровым днём — около сотни
подгонок, ~2 минуты. Каждые полчаса это 2900 минут Actions в месяц, вдвое выше
бесплатного лимита приватного репозитория.

Сторож (`src/watch.py`) делает три запроса на голой стандартной библиотеке, без
`pip install`, и укладывается в **10 секунд**. Полный прогон запускается только
когда есть повод:

* в расписании появился новый матч;
* БЕТСИТИ открыла линию на матч, которого у неё не было;
* Pinnacle подвинул цену больше чем на 2% — **главный повод**: валуй у мягкой
  конторы живёт ровно в окне, когда острый рынок уже уехал, а мягкий не догнал;
* БЕТСИТИ подвинула цену больше чем на 2% — прежний расчёт устарел.

Расход: ~37 прогонов сторожа в сутки (около 1100 минут в месяц) плюс полные
расчёты только по делу. Умещается в бесплатные 2000 минут. Если захочется
проверять каждые 10 минут — сделать репозиторий публичным, тогда минуты
Actions не ограничены.

Почему закрывающая линия снимается именно перед стартом: CLV считается
относительно неё, а API Pinnacle отдаёт только открытые рынки — после
стартового свистка цену уже не получить.

### Настройка

1. Создать репозиторий на GitHub и запушить этот проект.
2. В `Settings → Secrets and variables → Actions` добавить два секрета:
   - `TELEGRAM_BOT_TOKEN` — токен от @BotFather
   - `TELEGRAM_CHAT_ID` — свой id; получить так: написать боту любое
     сообщение и локально выполнить `python telegram_sender.py`
3. Проверить вручную: вкладка `Actions` → `UAE Pro League bets` → `Run workflow`,
   с галочкой `dry` для первого прогона.

### Локально

```bash
cp .env.example .env           # заполнить токен и chat_id
python bot.py --dry            # посчитать и напечатать, ничего не отправляя
python bot.py                  # посчитать и отправить
python bot.py --force          # переслать даже то, что уже отправляли
python bot.py --mode clv       # зафиксировать закрывающую линию
python bot.py --mode settle    # рассчитать сыгравшее и прислать сводку

python src/archive.py info     # что в архиве сырых ударов
python src/archive.py pack     # пересобрать архив из локального кэша
```

### Как устроено хранение

| Файл | Размер | Что внутри |
|---|---|---|
| `data/matches.csv` | 161 КБ | все матчи: счета, xG, удары, владение, коэффициенты Bet365 |
| `data/shots.csv` | 65 КБ | посчитанные поударные метрики: NPxG, xG с игры и со стандартов, xG при равном счёте, xGOT, пенальти |
| `data/shots_raw.jsonl.gz` | **420 КБ** | сырые удары целиком: xG и xGOT по каждому, координаты, часть тела, минута, тип ситуации |
| `data/bets_log.csv` | растёт | журнал: что советовали, по какой цене, какой был эталон, чем закончилось |
| `state.json` | мелкий | что уже отправляли, чтобы не слать дважды |

Сырой архив лежит в репозитории намеренно. В `shots.csv` метрики уже
посчитаны — если завтра понадобится новая (xG по зонам поля, по частям тела,
по 15-минуткам), из CSV её не достать. Архив хранит удары целиком: 374 матча,
4.6 МБ текста, 420 КБ в сжатом виде. Проект полностью пересобирается из
репозитория без единого запроса в сеть.

Не попадают в git только россыпь исходных json (16 МБ, локальный кэш для
скорости) и сохранённые страницы букмекера (14 МБ) — линия берётся через API.
`src/update_data.py` догружает лишь недостающее: обычно 3-5 запросов за прогон
вместо 800.

Линия БЕТСИТИ в CI берётся через их публичный запрос, поэтому сохранять
страницы вручную не нужно. Ручной режим с `.mhtml` остаётся для случаев,
когда нужны производные рынки сверх основных.

`state.json` помнит отправленные ставки, чтобы не слать одно и то же дважды.
Повторная отправка происходит, только если матожидание выросло минимум
на 3 п.п. — то есть линия реально сдвинулась.


## Быстрый старт: автоматический монитор

Страницы вручную сохранять больше не нужно — обе линии снимаются сами.

```bash
python src/monitor.py            # один прогон
python src/monitor.py watch 600  # проверять каждые 10 минут
```

Монитор берёт линию БЕТСИТИ с того же запроса, который делает их сайт
(`ad.betcity.ru/d/off/events`), линию Pinnacle с их публичного API, подгоняет
под Pinnacle распределение счёта и сравнивает с ним каждый коэффициент БЕТСИТИ.

Сигнал объявляется, только если перевес больше **удвоенной погрешности подгонки**
линии Pinnacle — иначе это шум метода, а не находка.

Всё пишется в `data/monitor_log.csv`, включая колонку «цена не менялась, ч» —
по ней видно, насколько БЕТСИТИ отстаёт от острого рынка.

## Ручной режим (если нужны дополнительные рынки)

Основной запрос отдаёт только главные рынки: 1X2, фора, тотал, двойной исход.
Для остальных 169 доп. исходов сохрани страницу матча (`Ctrl+S` -> «Веб-страница
полностью», формат `.mhtml`) в папку `Bets/` и запусти `value_report.py`.

```bash
python src/crawl_365.py       # догрузить матчи и статистику
python src/crawl_shots.py     # догрузить поударные данные (xG по каждому удару)
python src/build_shots.py     # посчитать NPxG, xG с игры, xG по счёту
python src/build_dataset.py   # собрать data/matches.csv
python src/value_report.py    # отчёт по туру и список ставок
```

Дальше — журнал ставок, чтобы понять, есть ли перевес на самом деле:

```bash
python src/clv.py log       # записать рекомендации + цену Pinnacle на момент ставки
python src/clv.py update    # перед самым стартом матчей: зафиксировать цену закрытия
python src/clv.py report    # средний CLV и его значимость
```

CLV — единственный практичный способ проверить перевес: стандартное отклонение
прибыли на ставку около 1.0, а CLV — около 0.1, то есть сигнал виден за десятки
ставок вместо тысяч.

## Как читать ярусы в отчёте

`value_report.py` делит ставки на три уровня. Разница между ними — не «сила сигнала»,
а то, чем именно подтверждается перевес.

Ранжирование идёт **по перевесу xG-модели**. Острая линия Pinnacle — не вето, а отдельная
колонка уверенности: она показывает, согласен ли с моделью самый информированный рынок.

| Ярус | Условие | Что про него известно |
|---|---|---|
| **1. Подтверждено** | перевес по модели **и** цена выше справедливой по Pinnacle | Единственный отбор с подтверждённой доходностью: Buchdahl, 24 150 ставок, ожидание +1.60%, факт +1.81% |
| **2. Рынок молчит** | перевес по модели, расхождение с Pinnacle в пределах погрешности подгонки (обычно ±3–4%) | Острая линия не подтверждает и не опровергает. Ставится, но с полным пониманием |
| **3. Рынок возражает** | перевес по модели, цена заметно ниже справедливой | Ровно такой отбор на 239 матчах дал **ROI −18.6%** (78 ставок) |
| **4. Эталона нет** | Pinnacle этот рынок не торгует | Проверить нечем |

Почему Pinnacle именно колонка, а не фильтр: проверка блендинга дала вес модели рядом с
рынком **−0.21** с интервалом [−0.88, +0.41] по ОАЭ и **+0.34** с интервалом [−0.51, +0.99]
по РПЛ. Ни один не значим. Данных не хватает, чтобы утверждать, что рынок всегда прав
против модели, — значит, отбрасывать по нему нельзя, но и игнорировать неразумно.

Почему ярус A обычно пуст: у БЕТСИТИ маржа около 8%, у Pinnacle 4.5–7%, и линии почти
совпадают по форме. На РПЛ, где есть 3149 матчей с обеими линиями, доля исходов выше
справедливой цены — **1.3% в одной средней конторе** против **50.6% при выборе лучшей цены
из ~40 контор** (ROI −18.4% и +3.1% соответственно). Плюс появляется от сравнения контор,
а не от качества модели.

## Модель

```
lambda_дом  = exp(mu + gamma + atk[дом]  - def[гост])
lambda_гост = exp(mu         + atk[гост] - def[дом])
P(x,y)      = Poisson(x|lambda_дом) * Poisson(y|lambda_гост)
```

Поправки Диксона-Коулза на низкие счета **нет**: `rho = 0`. Профиль правдоподобия
по ней даёт SE 0.124 и интервал [−0.20, +0.20] при оценке +0.030 — параметр
неидентифицируем на 370 матчах. Клетки 0:0 и 1:1, ради которых поправка и вводится,
лежат ровно на пуассоновском ожидании (obs/exp 0.98 и 0.99); вверх её тянут 0:1 и 1:0,
то есть асимметрия дом/гости, которую tau выразить не может. Снятие стоит −0.00038 RPS —
это упрощение, а не выигрыш.

Особенности реализации:

1. **Сила команд оценивается по xG с игры**, а не по голам. Пенальти (12.5% всего xG
   лиги), стандарты и автоголы выброшены по поударным данным как наименее повторяемые.
   Превосходство xG над голами воспроизводится на обоих окнах с большим запасом;
   различие между вариантами самого xG — в пределах шума.
2. **xG провайдера перекалиброван.** Множитель оценивается на обучающей выборке так,
   чтобы сумма целевой переменной совпала с суммой голов: сейчас **1.52** для xG с игры
   (для сырого xG было бы 1.21). Без поправки модель систематически занижала бы тоталы.
3. **Двухэтапная подгонка.** Сила команд — по xG (меньше шума), общий уровень
   результативности и преимущество поля — по реальным голам (на них принимаются ставки).
4. **Квази-пуассоновский вес.** Пуассоновское ядро предполагает Var = lambda, но у xG
   измеренная дисперсия Пирсона **0.49** против 1.01 у голов. Без поправки правдоподобие
   занижало информативность xG вдвое, а L2-штраф оказывался вдвое сильнее задуманного.
5. **Экспоненциальное затухание** веса матча, период полураспада **180 дней**.
6. **L2-сжатие** к среднему по лиге; новички лиги получают априор «слабее среднего».

Гиперпараметры: `half_life=180, alpha=0.30, w_goals=0.0, promoted_shift=0.25,
xg_cols=('h_xg_open','a_xg_open')`. Взяты **из теории, а не подобраны**: 108
конфигураций, оценённых на двух непересекающихся окнах, ранжируются между ними
**отрицательно** (Пирсон −0.26), а победитель первого окна занял на втором 105-е место
из 108. На выборке в ~120 матчей подбор ловит шум.

## Главный вывод валидации

Данные, не участвовавшие в выборе параметров (2026 год, 133 матча):

| Оценка | RPS |
|---|---|
| Модель | 0.17965 |
| Линия Bet365 | **0.17958** |

Практически вровень. Для сравнения, та же модель на голах вместо xG даёт 0.19089.

Тест на смешивание: оптимальный вес модели рядом с рынком **−0.21 с интервалом
[−0.88, +0.41]** по ОАЭ и **+0.34 с интервалом [−0.51, +0.99]** по РПЛ. Ни один не
значим — выборка не позволяет утверждать ни что модель добавляет информацию, ни что
не добавляет.

Поэтому линия Pinnacle используется как **мера уверенности, а не как фильтр**:
ранжирование идёт по перевесу модели, а согласие или несогласие острого рынка
показывается отдельной колонкой (ярусы 1–4 выше).
